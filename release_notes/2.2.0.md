# Version 2.2.0

This version has three non-trivial changes.

## Manifest dates

Manifest _created_ and _pulled_ dates are now stored and displayed in UTC (`YYYY-MM-DDTHH:MM:SSZ`).

> **The server auto-converts the cache on first start, which takes milliseconds.**

E.g., after startup `cat /var/lib/ociregistry/manifests/fd8112d* | jq` shows:

```json
{
  "type": 1,
  "digest": "ddbed11f...",
  "imageUrl": "quay.io/jetstack/cert-manager-cainjector@sha256:ddbed11f...",
  ...
  "created": "2026-03-25T22:24:31Z", <--- updated to UTC
  "pulled": "2026-11-14T18:57:51Z"   <--- "
}
```

Earlier releases used local time. As stated, on first start this server version and later converts existing dates on the file system before loading the in-mem cache, interpreting them in its current time zone. For Kubernetes deployments with the default image and chart, the local zone is UTC, so existing dates are unchanged apart from gaining a Z suffix. For servers on a host or with TZ set, don’t change the time zone in the same upgrade.

On conversion the server doesn't know whether a manifest was created under daylight savings time or non daylight savings time which could mis-state the UTC date by an hour. Since manifest dates really only serve the interests of pruning the cache, and the grain of pruning is likely days or weeks, this seemed like an acceptable conversion anomaly.

The CLI, REST API, and server background pruners now all require a converted manifest cache.

(Any automation scripts built around the server that parse list output should expect the new format.)

## Replace `labstack/echo`

The [echo](https://github.com/labstack/echo) server is a fine product but since most of the REST server scaffolding is implemented by [oapi-codegen](https://github.com/oapi-codegen/oapi-codegen) it turned out to be straightforward to eliminate one dependency and just use golang's [net/http](https://pkg.go.dev/net/http) package to run the http server.

I've load tested, and I run the server locally all day and so far I can't detect a difference...

## Optimize manifest pull date update

The server supports prune by pull recency so as to age stale images out of the cache. This requires to update the `pulled` date when a manifest is pulled. Earlier releases did this on every pull. This version only does it when a prior pull is more than an hour old. This better supports the common use case where - for example - a cluster spins up (or auto-scales) and many Daemonsets suddenly pull the same image at the same time. Now, only the first pull within the 1-hour window updates the pull date. This shortens the time window when the in-mem cache is locked. Prune timeframes that make sense to people are typically going to be days and weeks, so this small change improves concurrency without negatively affecting prune semantics.
