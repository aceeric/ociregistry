# Version 2.0.0

1. This release redesigned the manifest cache (in memory and on the file system) to properly support mutable tags.
   - The file system cache is auto-migrated when `serve` is run the first time.
   - New `migrate-cache` sub-command was created to migrate the cache by hand if desired.
   - Sub-commands `list`, `load` and `prune` require a migrated cache.
2. Implemented strict parsing of the configuration yaml provided to the server via the `--config-file` arg. Unknown or misspelled keys in the `--config-file` YAML now stop the server at startup.
3. Config yaml Prune configuration `dryrun` renamed to `dryRun` for consistency. (If your current configuration specifies `dryrun` the server won't start per number 2.)
4. Prune now _defaults_ to dry run. Installations that prune today will quietly stop pruning until they opt in:
   - config file: `dryRun: false`
   - prune subcommand: `--dry-run false`
   - REST: `dryRun=false`
5. Prune sub-command `--dry-run` now requires a value. A bare `--dry-run` is an error. Use `--dry-run true` or drop the flag.
6. Added `--no-cache` arg to `serve` and corresponding configuration yaml setting to enable always pulling mutable tags. Arg `--always-pull-latest` is supported for backward compatibility and is translated internally to `--no-cache ':latest$'`.
   - Matches tag and digest URLs.
   - The cached copy is served if the upstream pull fails.
   - Command-line patterns replace the config file's (rather than merging.)
   - Can be specified multiple times on the command line.
7. Added new diagnostic endpoint `/cmd/image/cache` for internal cache visibility.
8. Pruning
   - A prune blocks new upstream pulls while it runs; cached pulls aren’t affected.
   - If upstream pulls are still running after 10 seconds, the REST endpoint returns 503 and a scheduled prune is skipped until its next run.
9. URL canonicalization
   - Registry and repository names are lower-cased.
   - docker.io single-name images like docker.io/hello-world get stored as docker.io/library/hello-world but can still be re-pulled as originally pulled.
   - Tags are case-sensitive (prior version lower-cased.)
   - Prune, list and --no-cache patterns match the canonical URL, so docker.io/hello-world no longer matches for these operations.
10. Uses [imgpull](https://github.com/aceeric/imgpull) library `v1.16.0`, for anyone pulling large images over slow links
   - Bearer tokens are renewed during long pulls, including GitLab-style JWTs.
   - Blobs are checked against their digest, partial downloads are removed, and stalled downloads time out.
11. Also fixed some concurrency issues (prune racing with pulls, and partial files)

## Cache redesign

The pre-2.0.0 version didn't correctly support mutable tags. As a result the design for both the in-mem and file system cache had to change. When you start the 2.0.0+ server over a <2.0.0 cache (using the `serve` sub-command):
  - The cache is automatically one-time migrated from the old `lts` and `img` directories to the new `manifests` directory.
  - The migration is non-destructive: the old `lts` and `img` directories persist. You have to delete them if you choose at some subsequent time.
  - As before, the server builds its in-mem cache from the file system on startup every time so starting a >=2 server over a <2 cache results in: start > migrate file system > load cache into mem > serve.

Failed migrations: if any manifest can’t be written, there’s no completion marker and the server refuses to start. The details are in `manifests/migration-report.txt`, and the next start retries. Files that can’t be parsed are reported as skipped and don’t block the migration.

Every migration writes `manifests/migration-report.txt`, and a successful one also writes `manifests/migration-complete`, the marker that makes it one-time.

A pre-2.0 server run over a migrated cache sees only the old `lts` and `img` directories. If you then upgrade again, anything the old server pulled in the meantime is ignored, because the marker is already present. In other words, downgrading isn’t supported without restoring a pre-upgrade backup or manually manipulating the file system.

There's also a `migrate-cache` sub-command if you prefer it. The `--dry-run` arg shows what would happen without writing anything. Successful cache migration is a one-time process. Afterwards the server will only interact with the new file system cache. A >=v2 server started over an empty cache will initialize the file system in the new v2 format only.

## Understanding the new cache design

One way is by example.

> These examples use the [imgpull](https://github.com/aceeric/imgpull) CLI. Substitute with docker, crane, etc.

If:

```sh
imgpull localhost:8888/docker.io/hello-world:latest deleteme.tar --scheme http
```

Then the internal Go cache (pseudo-code) looks like:

```go
var mc (is the manifest cache) =
  entries map[cache.imageUrl]imgpull.ManifestHolder = [
    "docker.io/library/hello-world:latest"            : imgpull.ManifestHolder { (inside here digest is c567b231 ) }, // manifest list
    "docker.io/library/hello-world@sha256:d1a8d0a4...": imgpull.ManifestHolder { (inside here digest is d1a8d0a4 ) }, // image manifest
  ]
  aliases map[cache.digestUrl]cache.tagSet = [
    "docker.io/library/hello-world@sha256:c567b231...": {"docker.io/library/hello-world:latest": {}},
  ], 
```

There are two entries because a client pull is first a manifest list pull followed by an image manifest pull. So:

```sh
IMAGE_MANIFEST_DIGEST=d1a8d0a4eeb63aff09f5f34d4d80505e0ba81905f36158cc3970d8e07179e59e
imgpull localhost:8888/docker.io/hello-world@sha256:$IMAGE_MANIFEST_DIGEST deleteme.${IMAGE_MANIFEST_DIGEST:0:8}.tar --scheme http
```
Then:

```sh
$ ls -l delete*.tar
-rw-rw-r-- 1 frodo frodo 6656 Oct 28 18:41 deleteme.d1a8d0a4.tar
-rw-rw-r-- 1 frodo frodo 6656 Oct 28 18:31 deleteme.tar
```

They contain the same images (the same config and layers.) Then:

```sh
$ tar -xf deleteme.tar manifest.json --to-stdout | jq .[0].repoTags[0]
"docker.io/hello-world:latest"

$ tar -xf deleteme.d1a8d0a4.tar manifest.json --to-stdout | jq .[0].repoTags[0]
"docker.io/hello-world@sha256:d1a8d0a4eeb63aff09f5f34d4d80505e0ba81905f36158cc3970d8e07179e59e"
```

The imgpull cli reflects the pulled url in the `manifest.json`.

List the tarballs and observe they are the same images:

```
$ tar -tvf deleteme.tar

$ tar -tvf deleteme.d1a8d0a4.tar

-rw-rw-r-- frodo/frodo       347 2026-10-28 18:41 manifest.json
```

Inspect the server file system:

```sh
$ ls -lrt /var/lib/ociregistry/manifests/
total 32

-rw-r--r-- 1 frodo frodo 26190 Oct 28 18:39 05c465a76e627711836aef6167f264ee2114c8ef9eda772245231ecc412cc788

```

Validate that file system digests derive from the **manifest urls**:

```sh
echo -n docker.io/library/hello-world:latest | sha256sum | awk '{print $1}' && \
echo -n docker.io/library/hello-world@sha256:d1a8d0a4eeb63aff09f5f34d4d80505e0ba81905f36158cc3970d8e07179e59e  | sha256sum | awk '{print $1}'

05c465a76e627711836aef6167f264ee2114c8ef9eda772245231ecc412cc788
a1354e9c3499cba2bfb90aacd433a5d83ade06f0bae20041db72fc58078af4b4
```

Next:

```sh
IMAGE_LIST_MANIFEST_DIGEST=c567b231f65614688711a75f31518a064258a51d442117a3e771a3a8fdba78ef
imgpull localhost:8888/docker.io/hello-world@sha256:$IMAGE_LIST_MANIFEST_DIGEST deleteme.${IMAGE_LIST_MANIFEST_DIGEST:0:8}.tar --scheme http
```

Result:

```sh
$ ls -l delete*.tar
-rw-rw-r-- 1 frodo frodo 6656 Oct 28 19:11 deleteme.c567b231.tar
-rw-rw-r-- 1 frodo frodo 6656 Oct 28 18:41 deleteme.d1a8d0a4.tar
-rw-rw-r-- 1 frodo frodo 6656 Oct 28 18:31 deleteme.tar
```

So: Pulling the image list manifest by digest did the same as pulling by tag - it found the cached manifest list via the `latest` alias, then returned it to the caller, the caller picked the digest of the image manifest and requested it and it was returned.

Examine the in-mem cache:

```sh
$ curl localhost:8888/cmd/image/cache?digestLen=20
```

Output:

```text
ENTRIES:

ENTRY URL                                                     URL DIGEST               MANIFEST DIGEST          MANIFEST TYPE
docker.io/library/hello-world:latest                          05c465a76e627711836a...  c567b231f65614688711...  image list
docker.io/library/hello-world@sha256:d1a8d0a4eeb63aff09f5...  a1354e9c3499cba2bfb9...  d1a8d0a4eeb63aff09f5...  image

ALIASES:

ALIAS URL / TAGS
docker.io/library/hello-world@sha256:c567b231f65614688711...
    docker.io/library/hello-world:latest
```

Observe that the URL DIGEST column in the output matches the manifest filename on the file system from above.
